在现代微服务架构、分布式系统以及前后端分离的应用中，**JSON Web Token（JWT，RFC 7519 规范）** 已经成为了事实上的无状态鉴权标准。它提供了一种紧凑、URL 安全的载体，用于在各方之间以 JSON 对象的格式安全地传输身份声明（Claims）。

然而，许多开发者对 JWT 的底层机理缺乏足够了解，不恰当的集成方式常常让看似坚固的系统暴露出极其致命的身份越权漏洞。

---

## 一、 解剖 JWT 的底层结构

一个合法的 JWT 字符串由英文句点（`.`）分隔的三部分组成：

```text
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiYWRtaW4iOnRydWUsImlhdCI6MTUxNjIzOTAyMn0.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
└───────────────┬──────────────────┘ └─────────────────────────┬────────────────────────┘ └─────────────────────────────┬───────────────────────────┘
          Header (头部)                             Payload (载荷)                                   Signature (数字签名)
```

1. **Header（头部）**：包含令牌的元信息，通常声明令牌类型（`JWT`）以及所使用的签名算法（例如 `HS256`、`RS256`）。
2. **Payload（载荷）**：包含具体的声明数据（Claims），例如签发主体、过期时间戳（`exp`）、用户 ID 及角色权限等。
3. **Signature（签名）**：由服务端使用特定密钥对编码后的 Header 与 Payload 进行密码学运算生成的摘要，用于验证传输过程中数据是否被篡改。

## 二、 开发者最常踩的三大安全雷区

### 1. "None" 算法伪造漏洞（The None Algorithm Attack）
某些陈旧或配置不当的后端校验库，允许客户端将 Header 中的算法字段指定为 `alg: "none"`。一旦服务端疏忽允许此配置，攻击者只需将签名部分留空，就能直接伪造任意包含管理员权限（如 `admin: true`）的合法 Token！
* **防御手段**：服务端在验签时，必须显式对允许的算法进行**白名单强校验**（如只允许 `HS256` 或 `RS256`），坚决拒绝未加密签名的请求。

### 2. 对称与非对称密钥混淆（Key Confusion Attack）
当系统使用 `RS256`（非对称加密：公钥验签、私钥签名）时，服务端的公钥往往是对外公开的。如果攻击者将 Header 强行篡改成 `HS256`（对称加密：相同密钥既可签名又可验签），而服务端验签代码错误地将公钥作为 HS256 的密钥传入，攻击者就能直接用公开的公钥自行生成完全合法的篡改令牌！
* **防御手段**：坚决在鉴权逻辑中强制绑定具体密钥类型与对应算法，绝不可动态依赖客户端传入的 `alg` 字段。

### 3. 将敏感明文塞入 Payload（严重隐私泄露）
**很多新手最普遍的误区是认为 JWT 是“加密”的。**
事实上，JWT 的 Header 和 Payload **仅仅是简单的 Base64URL 编码，任何人拿到 Token 都能一键还原成明文！** 绝不可在 Payload 中存储明文密码、数据库连接串、身份证号等高度敏感信息。

## 三、 现代 Web 鉴权最佳工程实践

* **双 Token 机制**：保持 Access Token 的生命周期足够短暂（10 ~ 15 分钟），同时配备保存在 `HttpOnly` Cookie 中的持久 Refresh Token，兼顾无状态性能与主动踢出恶意会话的安全性。
* **本地化安全解析调试**：在排查前后端鉴权联调问题时，尽量避免使用将 Token 传输给远端第三方服务器的在线解析器，推荐使用完全基于纯前端本地运行的工具（例如 **[XPT Dev JWT 解析器](https://tools.xptdev.com/#/jwt-parser)**），确保密钥与用户凭证 100% 不离线泄露。
